# Plan: Mock Demo Frontend — Smart Sneaker Showcase UI

> **Phase:** Plan · **Status:** draft · **Date:** 2026-07-11
> The *how*. Derived from `spec.md`. Must not contradict the spec; if it does, fix the spec first.
> All `[NEEDS CLARIFICATION]` markers in the spec MUST be resolved before this phase. (Spec status: clarified 2026-07-10.)

## Summary

Add one new workspace, `apps/demo-web`: a static React + TypeScript single-page app (Vite) that
renders the six screens from the Claude Design prompt (session list, session insights, trends,
live capture, coach view, pipeline status). It displays **only pipeline-produced data**: a small
generator in `tools/e2e` runs the existing in-memory full pipeline (ingest → worker → dashboard
reads → e2e scenario checks) over the seed corpus — exactly what `pipeline.test.ts` already wires
up — and emits a single `demo-data.json` artifact the app loads at startup. The capture screen
replays a deterministic synthetic run *in the browser* using the insights engine's own
`generateSyntheticRun`, so no raw sample data ships in the artifact. The seed corpus is extended
with the sessions Req. 7 and the trends view need (a ~12-session trend series, a low-confidence
session, a still-processing session, an errored session). Visual language comes from the Claude
Design prototype (Req. 13) and is implemented via the existing `packages/design-system` tokens
and components, extended as the prototype demands.

## Architecture

The demo is a **read-only static frontend over a build-time pipeline run**. No server runs at
demo time — which satisfies self-contained local use (Req. 8) and the "hostable later, no
localhost assumptions" non-goal in one move (a static bundle can go to any static host).

```
                    ── generation time (node, in-memory, seconds) ──
tools/e2e buildSeedCorpus()
   │  users / grants / sessions (deterministic, contract-valid)
   ▼
in-memory pipeline run (same wiring as pipeline.test.ts):
   ingest API (real HTTP boundary) → published events → session worker
   → authoritative SessionResults → dashboard-style queries (athlete lists,
     trends, coach roster via grants) → per-stage / per-scenario pass-fail
   ▼
apps/demo-web/public/demo-data.json   (gitignored; regenerated by `predev`/`prebuild`)
   personas (no tokens) · session summaries · session results (insights +
   confidence + flags) · trend series · coach roster · pipeline status

                    ── run time (browser only) ──
demo-data.json ─→ data layer (validated load, persona gating, state derivation)
                     │                                  ▲ unit-tested pure logic
                     ▼
        React views (Vite SPA, hash routing)
        SessionList · SessionDetail · Trends · Capture · Coach · PipelineStatus
                     │
        @smart-sneaker/design-system (tokens + DemoBadge, ConfidenceBadge,
        InsightCard, StatusChip, …) ⇄ Claude Design prototype (Req. 13)

        Capture view: @smart-sneaker/insights-engine generateSyntheticRun()
        replayed on a timer (incl. scripted dropout → "Reconnecting…" state)
```

Component responsibilities:

- **`tools/e2e` (extended):** owns seed-corpus additions and a new `write-demo-data.ts` entry
  point. It is the only place that imports the service packages (ingest, worker, dashboard) —
  the browser app never does, keeping the frontend dependency graph tiny and browser-safe.
- **`apps/demo-web/src/data/`:** loads and validates `demo-data.json`, derives view state
  (status chips, confidence levels via the design system's `describeConfidence`, persona
  filtering). All pure functions — the unit-test surface the constitution demands.
- **`apps/demo-web/src/views/`:** the six screens, presentational, fed by the data layer.
  Insight numbers only ever arrive via props from pipeline-produced data (Req. 6 — enforced by
  a generator/UI spot-check test, see Testing).
- **`packages/design-system`:** grows whatever primitives the Claude Design prototype
  establishes (chart, split bar, app shell / tab bar, persona switcher). Stays the sync source
  for Claude Design per the existing DesignSync setup.

Smallest-change notes: no new service, no runtime backend, no duplication of insight logic; the
generator reuses the e2e harness wiring rather than re-implementing pipeline steps.

## Stack & Dependencies

Defaults from `~/development/memory/preferred_stack.md`, with one recorded deviation:

- **Language/Framework:** TypeScript (strict) + React 19 — per stack default and the existing
  design-system peer range. **Vite SPA instead of Next.js** — deviation recorded as
  **ADR-0003** in `~/development/memory/architecture_decisions.md`: the demo is a pure
  client-side mock with no SSR/data-fetching/SEO needs, must build to plain static files for
  later hosting, and Vite matches the repo's existing plain-`tsc`/ts-jest toolchain far more
  lightly than Next's build pipeline.
- **Routing:** `react-router-dom` with **hash routing** — deep-linkable screens for design
  review without assuming any host rewrite rules (no localhost-only or server-config
  assumptions, per Non-Goals).
- **Styling:** design-system tokens (`tokens.css` / `tokens.ts`) + CSS modules. No Tailwind:
  the design system is already hand-rolled tokens synced to Claude Design; introducing a second
  styling system would fork the visual source of truth.
- **Charts:** hand-rolled SVG chart components inside `packages/design-system` (one line chart
  with range band + highlighted point, one split bar). At tens of points, a charting library
  buys nothing and costs bundle size and a11y control (visible axes/units and non-color
  encoding are hard requirements). Trade-off named below.
- **Data store:** none at runtime — a generated, schema-validated JSON artifact. Firestore &
  friends stay behind the generation step's in-memory adapters.
- **New dependencies:** `vite`, `@vitejs/plugin-react`, `react-dom`, `react-router-dom`,
  and for tests `@testing-library/react` + `jest-environment-jsdom`. All mainstream,
  well-audited, dev-or-demo-scoped. Nothing new in production services.

## Data Model

No persistent store. The artifact contract is the data model — defined as zod schemas in
`apps/demo-web/src/data/demo-artifact.ts` (demo-only shapes; `SessionResult` etc. are imported
from `@smart-sneaker/data-contracts`, not redefined):

- **`DemoPersona`** — `{ id, displayName, role: 'athlete' | 'coach' }`. Derived from the seed
  roster **with bearer tokens stripped** at generation time (they never reach the artifact).
- **`DemoSessionSummary`** — per session: `sessionId`, `slug`, `startedAtMs`, `sportProfileId`,
  `durationMs`, `status: 'synced' | 'processing' | 'on-phone-only'`, `dataQualityWarning?`,
  `flaggedForReview`, `ownerAthleteId`.
- **`DemoSessionDetail`** — the worker's `SessionResult` (authoritative insights with per-insight
  confidence, reliability, notes, per-foot keying) plus consistency/`computedBy` info for the
  "computed on phone / verified in cloud" indicator. For the errored seed session: the
  `failed-validation` result the worker persists.
- **`DemoTrendSeries`** — per athlete, per metric: ordered `{ sessionId, startedAtMs, value }[]`
  (ordered by `sessionStartedAtMs`, matching the dashboard's decision that trends order by when
  sessions happened).
- **`DemoCoachRoster`** — per coach: athletes **derived from seed sharing grants at generation
  time** with last-session summaries. Athletes without a grant (Chike) are absent from the
  artifact's coach view entirely — the visibility model is enforced upstream of the UI, so the
  UI cannot leak what it never receives (Req. 5).
- **`DemoPipelineStatus`** — five stages (capture → segmentation/insights → ingest → worker →
  results), each `pass | fail | running`, plus per-scenario entries mirroring the e2e
  expectations (incl. the invalid-session-rejected-with-400 probe) with pass/fail and
  description (Req. 12).

Seed-corpus additions (in `buildSeedCorpus()`, so the existing e2e suite exercises them too):

1. **Trend series:** ~9 more Asha running sessions across ~6 weeks with gently drifting cadence
   and balance parameters (~12 total for the trends chart).
2. **Low-confidence session:** heavy multi-window dropouts so at least one insight lands below
   the engine's reliability bar (confidence < 0.6 or < 4 cycles) → Req. 7b.
3. **Still-processing session:** a normal session listed in generator config as *withheld from
   the worker stage* → summary status `processing`, no detail result → Req. 7a.
4. **Errored session:** a blob the worker fails validation on (injected at the blob layer by
   the generator, mirroring the worker's persisted `failed-validation` path) → error state,
   Req. 7d. Empty state (Req. 7d's empty half) comes free: a persona view with zero sessions
   (e.g. a fourth athlete with no sessions, or coach-side athlete with none).
   The existing `ben-dropout-run` already provides the data-quality warning (Req. 7c).

## API Contract

No network API at runtime. Two contracts instead:

- **Generator CLI:** `npm run demo-data --workspace @smart-sneaker/e2e` → writes
  `apps/demo-web/public/demo-data.json`; exits non-zero (and writes nothing) if any
  pipeline stage produces an unexpected outcome, so a broken pipeline can't silently ship a
  stale-looking demo. Wired as `predev`/`prebuild` in `apps/demo-web`, making the documented
  run command exactly: `npm install && npm run dev --workspace @smart-sneaker/demo-web`
  (Req. 8, acceptance criterion 1).
- **Artifact schema:** the zod schemas above; the app refuses to render on an invalid artifact
  (fail loudly with the error/empty-state screen — which is itself a Req. 7 deliverable).

Routes (hash): `#/sessions`, `#/sessions/:id`, `#/trends`, `#/capture`, `#/coach`,
`#/pipeline`. Persona is app-shell state (context), switchable without reload (Req. 10);
switching to coach lands on `#/coach`, athlete routes hidden for the coach persona.

## Security & Privacy

- **All data synthetic:** seed corpus only; personas are fictional. Generator strips seed bearer
  tokens from the roster before writing the artifact, and a unit test asserts the artifact
  contains no `token` fields — nothing credential-shaped ships to the browser (Security NFR).
- **Simulated auth, labeled:** persona switching is presentation-only gating; the persistent
  `DemoBadge` on the app shell (every route) plus a note on the persona switcher make that
  explicit (Req. 9). Real enforcement remains server-side in the real dashboard — the demo's
  coach filtering happens at generation time from real sharing grants, so screenshots are
  truthful about the product's visibility model without claiming enforcement.
- **XSS surface:** React's default escaping only; no `dangerouslySetInnerHTML`; all displayed
  strings originate from our own generator. Artifact is schema-validated at the boundary
  (treat even our own file as untrusted input, per the constitution).
- **No secrets/config:** no env vars, no cloud SDKs, no network calls in the app bundle.
- **OWASP relevance is minimal by design** (static, read-only, no auth, no inputs beyond
  clicks); the one real risk — someone mistaking the demo for a real product with real access
  control — is addressed by Req. 9's badge and the non-goal that hosting ships in a later spec.

## Observability

Demo-scale, deliberately light (Scale NFR): the generator logs a one-line summary per stage and
per scenario (mirroring `write-seed.ts` style) so a failed generation is diagnosable from CI
output; the app ships a top-level React error boundary that renders the designed error state
(never a blank page or raw stack — consumer-facing bar) and `console.error`s the cause for the
developer. No metrics/traces — there is no production surface.

## Testing Strategy

Jest + ts-jest everywhere (constitution's decided framework); `jest-environment-jsdom` +
Testing Library for component tests. Mapped to acceptance criteria:

- **Generator (integration, node):** running the generator over the corpus produces an artifact
  that (a) validates against the artifact schema, (b) contains all four Req. 7 trigger states,
  (c) contains ≥10 sessions in Asha's trend series, (d) has a coach roster that includes Asha +
  Ben and **excludes Chike** (AC 4's data half), and (e) is byte-identical across two runs
  (determinism, keeps `predev` honest).
- **Req. 6 spot-check (the anti-hard-coding test):** a test recomputes
  `computeSessionInsights` over a seed session and asserts the artifact's stored insight values
  equal the recomputation; a second check greps `src/views/` for numeric insight literals is
  *not* attempted (brittle) — instead component tests assert views render values passed from
  artifact fixtures, and the artifact is the only data import allowed in views (enforced by an
  ESLint `no-restricted-imports` rule on `src/views/**`). Together these satisfy AC 3.
- **Data layer (unit):** persona gating (coach sees only granted athletes; athlete sees only
  own sessions), status derivation (synced/processing/on-phone-only), confidence-level mapping,
  trend-series ordering by `startedAtMs`, artifact-validation failure → error state.
- **Capture replay (unit, fake timers):** elapsed time, packet-rate indicator, scripted dropout
  → `Reconnecting…` with data-retained message → recovery; End Session transitions (Req. 4).
- **Component render tests (Req. 7 / AC 5):** each non-happy state renders its designed,
  visually distinct treatment: processing chip, low-confidence badge (icon + label, not
  color-only), data-quality warning, unreliable insight with note, error and empty states.
  DemoBadge asserted present in the app shell (AC 6).
- **Pipeline status view:** renders five stages and per-scenario pass/fail from artifact
  fixtures, including a failing-scenario fixture (AC 8).
- **Manual/visual (documented in the workspace README, not automated):** phone-width and
  desktop-width review (AC 7), first-render feel (Perf NFR), and the Claude Design
  prototype-vs-implementation review (AC 9 — inherently human judgment; the prototype exports
  live under `specs/002-mock-demo-frontend/design/`).
- **CI:** the workspace's tests run under the root `npm test --workspaces` like every other
  workspace (AC 10); generator test doubles as the freshness check.

## Risks & Trade-offs

- **Risk:** seed-corpus growth (~9 sessions × 100 Hz × 2 feet) slows the existing e2e suite and
  bloats `npm run seed` fixtures. → **Mitigation:** trend-series sessions stay short (30–45 s —
  the engine's insights don't need long sessions) and the artifact stores *results only*, never
  raw samples; if e2e time degrades, the trend sessions can be generated only for the demo
  artifact (kept out of the ingest-boundary e2e stage) without changing the design.
- **Risk:** engine parameters don't produce the intended low-confidence state (confidence is
  emergent, not settable). → **Mitigation:** the generator *asserts* the state exists and fails
  loudly; tuning dropout windows against the real reliability rule (< 0.6 confidence or < 4
  cycles) is an explicit early task, not a hope.
- **Risk:** Claude Design prototype and coded UI drift (Req. 13/AC 9 is judgment-based). →
  **Mitigation:** design-first task ordering — prototype iterated and exported *before* view
  implementation; design-system components (already DesignSync-linked) are the shared
  vocabulary between both.
- **Risk:** "pipeline status" screen shows stale results if someone edits pipeline code without
  regenerating. → **Mitigation:** artifact is gitignored and regenerated on every `dev`/`build`
  via `predev`/`prebuild`; generation is seconds (in-memory).
- **Trade-off:** optimized for **self-containment and hostability** (static SPA over generated
  artifact), gave up **live recomputation in the browser** (the demo won't reflect engine edits
  until regeneration) — acceptable because regeneration is automatic on every run, and shipping
  the service packages to the browser would be heavier and less true to the real architecture.
- **Trade-off:** optimized for **a11y control and zero chart dependencies** (hand-rolled SVG
  charts), gave up **free interactivity/animation from a chart library** — acceptable at one
  line chart + one split bar; revisit (Recharts) if the trends view grows real interaction
  requirements.
- **Trade-off:** Vite over the Next.js default (ADR-0003) — optimized for toolchain fit and
  static output, gave up a ready-made path to SSR/API routes the demo explicitly doesn't need.
